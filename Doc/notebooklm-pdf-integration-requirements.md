# NotebookLM PDF 知识集成需求（V1）

状态：可实施基线
范围：PDF 原理图、NotebookLM 文档检索及当前已确认的协作场景

## 1. 目标

在不把芯片手册等资料复制进项目目录的前提下，让 Codex 能够：

- 从项目内选定的 PDF 原理图提取 MCU、驱动芯片、MOS 等关键器件；
- 将器件与 NotebookLM 中已有的芯片手册和相关资料建立可持久化的来源绑定；
- 在日常开发中按需进行有来源约束的精准检索；
- 显式上传新资料、替换旧版本并维护项目经验；
- 让 `project-init`、`project-sync` 与独立的 `notebooklm-reference` Skill 共用同一套规则。

## 2. 初版范围

### 2.1 包含

- 仅将 PDF 作为原理图输入格式；支持文字型 PDF 和扫描型 PDF。
- 可同时绑定项目专属 Notebook 和一个公共芯片资料 Notebook；启用时至少绑定其中一个。
- 支持 `search`、`refresh`、`upload`、`save-experience`、`status` 五类 Skill 场景。
- 支持无原理图但仍需使用 NotebookLM 的手动检索模式。
- 支持连接检查、认证恢复、来源刷新、版本替换、经验管理和文档冲突仲裁。

### 2.2 不包含

- 前端、后端等通用项目需求文档的自动索引。
- 杂乱 Markdown 随记的整理和上传。
- PDF 之外的原理图格式。
- 自动定时刷新 NotebookLM 来源。
- init/sync 静默上传项目文件或整张原理图。
- NotebookLM Research、音视频/测验生成和共享权限管理。

## 3. 持久化状态

项目使用 `.agent/notebooklm-index.json` 保存 NotebookLM 的账户绑定本地状态。该文件：

- 不包含凭据、Cookie、Token 或账户邮箱；
- 不提交 Git，并且不修改项目共享 `.gitignore`；
- 保存模式、Notebook ID、原理图身份、器件映射、Source/Note ID、刷新时间、待确认项和错误状态；
- 将来源清单视为手动刷新后的缓存，而不是 NotebookLM 当前状态的永久事实。

文件不存在表示 `unconfigured`；fresh init 和升级后首次 sync 都必须询问一次。文件存在但缺少 `mode` 或不符合 schema v1 时表示 `invalid`，任何 context、索引或 `AGENTS.md` 写入前停止。`disabled` 持久化“不再询问”，重新启用必须显式 configure。

索引至少表达以下逻辑信息：

- `mode`：`schematic`、`manual` 或 `disabled`；
- 原理图分析是否已被用户明确关闭；
- 主原理图的项目相对路径和 SHA-256；
- 零或一个项目专属 Notebook 与零或一个公共芯片资料 Notebook 的稳定 ID；启用状态至少存在一个绑定；
- 器件位号、完整型号、类别、封装、PDF 页码、识别置信度和来源绑定；
- 经验 Note 的主题、适用范围和稳定 ID；
- 最近一次手动来源刷新的时间及当前告警。

## 4. `AGENTS.md` 约束

NotebookLM 启用时，插件只在 `Project Context` 中增加一行：

```md
- `.agent/notebooklm-index.json`: NotebookLM reference bindings and document-retrieval state.
```

所有检索、上传、认证、经验和冲突规则保存在 Skill 及其参考文件中，不在 `AGENTS.md` 重复展开。

NotebookLM 为 `disabled` 或 `unconfigured` 时不增加该行。重复初始化、同步或 configure 不得重复插入该行，也不得修改托管边界之外的用户内容。

## 5. 初始化流程

### 5.1 连接预检

当项目启用 NotebookLM 时，`project-init` 必须先检查 MCP 可用性和认证状态。

- 未连接或认证失效时，暂停后续生成并引导用户完成连接或重新认证；
- 用户明确选择本次跳过后，排除 NotebookLM 并继续初始化；
- 用户完成恢复后，从连接预检继续，不重复已经确认的项目选择；
- 连接决策完成前，不写入半完成的 NotebookLM 索引或 `AGENTS.md` 内容。

### 5.2 原理图选择

- 仅允许一个主 PDF 原理图；保存项目相对路径和文件哈希。
- 存在多个候选 PDF 时询问用户，不自动合并。
- 扫描型或模糊 PDF 可以使用 OCR 辅助识别，但不得猜测不完整型号。
- 每个识别结果应保留位号、型号、封装、页码和置信度；歧义项进入待确认列表。

### 5.3 启用选择与未检测到原理图

无论是否检测到 PDF，初始化都先取得一次启用选择；PDF 只作为 `schematic` 推荐依据。未检测到原理图时提供以下选择：

1. 用户指定一个未被识别的 PDF 原理图；
2. 不分析原理图，但启用 NotebookLM 手动检索模式；
3. 禁用本项目的原理图分析和 NotebookLM 集成。

选择 `manual` 只关闭原理图分析，仍启用 NotebookLM；选择 `disabled` 才会让后续 `project-init` 和 `project-sync` 不再询问，即使以后出现 PDF。重新启用必须由用户主动发起。

### 5.4 器件提取

初版索引以下器件：

- MCU；
- 驱动芯片；
- 电源、通信和传感芯片；
- MOS。

普通阻容不建立手册索引。可见阻值、容值和连接关系只作为 Agent 的本地分析上下文，不需要额外授权，也不默认发送给 NotebookLM。

### 5.5 Notebook 绑定和初始来源映射

- 项目专属 Notebook 和公共芯片资料 Notebook 各允许零或一个，启用时至少绑定一个，也允许二者同时使用。项目库/公共库是知识适用范围，MCU/Driver/MOS/Other IC 是文档类别，两者不可混作同一分类字段。
- 绑定使用稳定 ID，不通过名称静默猜测。
- 多个候选 Notebook 无法唯一确定时询问用户。
- 初次初始化允许读取紧凑来源清单并为器件建立候选 Source 绑定。
- `project-init` 不自动上传原理图或缺失手册；可以提示用户使用 Skill 的 `upload` 场景。

## 6. 同步流程

`project-sync` 只同步已启用的 NotebookLM 项目状态：

- 自动比较主 PDF 原理图的 SHA-256；
- 原理图变化时重新提取器件并更新器件映射；
- 新器件在现有来源缓存中没有匹配项时记录告警并建议手动刷新；
- 不因时间经过而刷新来源，不设置 TTL；
- 只有用户明确要求刷新 NotebookLM 索引时才重新读取来源清单；
- 原理图分析已关闭时不重新询问或自动开启；
- 同一输入重复同步必须保持索引和托管 `AGENTS.md` 字节稳定。

## 7. `notebooklm-reference` Skill 场景

### 7.1 `status`

- 检查 MCP 连接、认证状态和当前 Notebook 绑定；
- 报告索引模式、原理图状态、最近刷新时间和待确认项；
- 认证失效时进入统一恢复流程。

### 7.2 `search`

- 从用户需求中提取目标器件和问题；
- 默认只向 NotebookLM 发送器件身份、文档版本条件和检索需求，不发送整张原理图；
- 在每个 Notebook 内使用确定的 `source_ids` 进行限定检索；
- 分别查询项目库和公共资料库，再由 Agent 合并带引用结果；
- 普通检索不自动执行来源刷新；
- Source 失效或映射不存在时暂停确定性结论，并建议用户手动刷新；
- 涉及寄存器、引脚、电气限制、时序、初始化序列、Errata 或芯片选型依据时可以自动触发该场景。

### 7.3 `refresh`

- 仅由用户明确请求触发；
- 使用紧凑来源清单识别新增、删除、失效和版本变化；
- 更新器件到 Source 的绑定及 `lastRefreshedAt`；
- 不设置基于时间的自动过期规则。

### 7.4 `upload`

- 用户明确要求上传时才能执行，不静默上传；
- 目标 Notebook 和文件明确时，用户的上传请求即构成授权；
- 目标不明确、发现疑似重复，或涉及非确定性替换时暂停确认；
- 通用芯片手册、Reference Manual 和 Errata 默认进入公共芯片资料库；
- 项目规范、测试报告和项目相关资料默认进入项目专属库；
- 等待新 Source 处理完成并验证可读后再更新索引。

独立资料库上传调用为 `$notebooklm-reference upload <PDF 根目录>`，不要求项目、原理图或 `.agent`。它只面向一个用户绑定的公共资料 Notebook；未绑定时提示绑定，只有用户明确要求才创建 Notebook。可在另一台电脑上对实际 PDF 根目录执行同一命令。

独立上传仅递归扫描 PDF，不跟随符号链接，不修改本地文件。它读取文件名、PDF 元数据、首页和必要正文，将资料按 MCU、Driver、MOS、Other IC 归类，并识别 Datasheet、Reference Manual、Errata、Application Note、硬件设计指南等类型。高置信且目标唯一时可直接上传；型号、类别、版本或重复关系不确定时进入待确认。

PDF 根目录保存 `.notebooklm-upload-manifest.json`，只包含相对路径、SHA-256、文件属性、分类、厂商/型号、文档类型/版本、公共 Notebook、Source ID 和处理状态。该 manifest 用于增量扫描、重复跳过和替换判断，不含认证信息。

版本替换固定使用以下顺序：

1. 上传新版；
2. 等待新版 Ready；
3. 验证文档编号、目标芯片、适用修订和内容身份；
4. 更新来源绑定；
5. 删除确定被替代的旧 Source。

任一步失败都保留旧 Source。不同芯片修订对应的资料不视为可直接删除的旧版本。

### 7.5 `save-experience`

当结果满足以下任一条件时，Agent 可以提出经验候选：

- 解决了非显而易见的芯片问题；
- 完成了经测试验证的参数选择；
- 发现芯片或板级特殊行为；
- 完成了文档冲突仲裁；
- 形成可复用的调试流程；
- 确认故障原因和有效修复。

普通手册摘抄、临时猜测和日常开发进度不形成经验。

- Agent 自动识别候选并展示简短草稿，用户确认后保存；
- 用户明确调用 `save-experience` 时直接保存；
- 默认只保存具有手册引用、代码、测试、波形、日志或可重复现象支持的内容；
- 用户明确要求时可以保存为 `provisional`，检索时不得视为已验证结论；
- 芯片通用经验保存到公共资料库，项目和板级经验保存到项目专属库；
- 每个芯片或主题维护一个可更新的 Note，不创建多个互相冲突的 Note；
- 后续证伪时更新原 Note 并移除错误结论；适用条件不同则并列记录条件。

## 8. 文档冲突仲裁

Agent 按以下顺序评估来源，但必须同时检查芯片型号、硅修订、封装、文档版本和工作条件：

1. 匹配芯片版本的官方 Errata 和限制；
2. 官方 Datasheet 和 Reference Manual；
3. 官方应用笔记；
4. 项目实测记录；
5. 芯片厂商技术支持材料；
6. 经销商或第三方资料。

当适用条件和权威性足以判断时，由 Agent 仲裁并说明理由。涉及绝对最大额定值、安全限制，或官方资料之间仍无法消解的冲突时，暂停并询问用户。项目经验可以解释实际行为，但不能覆盖官方安全限制。

## 9. 失败与降级

- NotebookLM 是当前任务所需证据来源时，连接失败必须暂停依赖该证据的生成。
- 用户明确选择跳过后可以继续，但必须标记结论未经 NotebookLM 验证。
- OCR 歧义、Source 缺失、版本不确定或来源冲突不得通过猜测消除。
- NotebookLM 不可用不得破坏已有 `.agent/context.json`、handoff、plan 或用户编写的 `AGENTS.md` 内容。

## 10. 验收标准

- 启用 NotebookLM 的项目只在 `AGENTS.md` 增加一条索引入口；禁用项目增加零条。
- 没有原理图时只询问一次；用户关闭后重复初始化和同步均不再询问。
- 手动模式可以在没有原理图和器件清单的情况下绑定 Notebook 并执行检索。
- PDF 变化触发器件重提取，但不触发 NotebookLM 来源自动刷新。
- 普通检索不调用来源清单刷新；显式 `refresh` 能发现后续新增资料。
- 多 Notebook 检索分别限定来源并保留可追溯引用。
- 认证失效会暂停依赖文档的工作，用户跳过后才允许降级继续。
- 新版未 Ready 或身份验证失败时不删除旧版。
- 经验候选未经确认不写入；显式保存可以直接写入。
- 重复 `init` 或 `sync` 不重复托管内容，并保持非托管文件内容不变。
- 索引不存储凭据或账户邮箱，并保持账户绑定本地状态不进入 Git。
- 独立上传只扫描 PDF，重复扫描能跳过未变化的 Ready 文件，并在新版未验证或未 Ready 时保留旧 Source。

## 11. 初版后的扩展方向

以下能力仅作为后续方向，不属于本次实现：

- 前端、后端和通用软件项目的需求、API、架构、数据库及运维文档索引；
- 对非结构化 Markdown 随记进行拆分、脱敏和 Source/Note 路由；
- 其他原理图格式及更专业的 BOM/EDA 解析；
- Research、Studio 生成和共享管理。
